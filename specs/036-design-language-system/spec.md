## 1. Problem and outcome

**Problem:** TeamBeats grew screen by screen. Without one written design language, each feature chose its own spacing, wording, icons and states, contrast was checked only in places, and customers could change colors but not choose a look that fits them (a ministry wants something formal, a retail group something bold). Designers had no shared rules to test against and developers had no gate to stop drift.

**Outcome:** One design language system that is also an experience system: it governs single parts and how whole pages are composed from them. It is modeled on national design systems such as the UAE Design System, with design guidelines (typography, colour, icons, imagery, content, layout, actions, accessibility), technical guidelines (frontend practice, security, performance, consistency), ready components and templates, and a testing strategy for designers and developers. TeamBeats ships four complete designs that tenant administrators choose from; the current v2 look (Beats) is the default. A design is a visual personality: its tokens, its navigation style, its default density and the presentation variant it uses for shared parts. Every page, for employees and for administrators alike, is composed by the same rules: it leads with what the person must do, keeps summaries inside a content budget, never repeats a data source, and shows every state. The component library covers what a modern product interface needs (actions, selection, text entry, pickers, dates, overlays, structure, status, data blocks, assistant parts, charts and page patterns), each built once on the tokens so every design gets it. The build enforces the system, and the constitution makes it binding.

## 2. Scope

**In scope:**
- Design and technical guidelines in `docs/design-system`.
- Four designs: Beats (default), Atlas, Pulse, Studio, each a complete accessible token set plus a navigation style.
- Design choice per brand in the brand manager (spec 033), inherited and lockable like any token.
- Shared component library and gallery: buttons, text boxes, text areas, selects, cards, badges, avatars, alerts, images, tabs, icons, states, skeletons, confirmations, selection bar, messages.
- The extended catalogue (section 5, DLS-030 to DLS-041): actions, selection controls, text entry, pickers and menus, dates, overlays, structure, status, data blocks, assistant and agent parts, charts and page patterns. The catalogue was drawn up from a study of the BoardUI component library; every component is TeamBeats code on TeamBeats tokens, and no third-party component code or component library is used.
- Page template patterns mapped to the spec 032 templates.
- Automated consistency gate and design test suite; manual design testing process.
- Enforcement: constitution principle XXXI, spec template, CLAUDE.md, references in specs 007, 008 and 033.
- Experience rules (DLS-100 to DLS-119): page hierarchy, content budgets, one instance per data source, state completeness, type roles and the text size floor, the page frame, the filter toolbar, the pattern choice table, work rows that act, design descriptors with presentation variants, visualization, editorial, identity, assistant and form patterns, one system for administration and employee screens, and gates that reach the product's main pages.

**Out of scope:**
- Customer-specific designs written in code. Customers adjust a design through tokens (spec 033).
- Native mobile app design (spec 030 adopts these guidelines when it starts).
- Marketing website design.
- An image generation screen: no approved spec has that feature, so no component is built for it.

## 3. Actors and permissions

| Actor | What they can do in this feature | Permission / scope required |
|---|---|---|
| Tenant administrator, brand manager | Choose the design for the tenant brand, adjust tokens on top, publish | `theme.edit`, `theme.publish` (spec 033) |

| Employee | Sees the effective design; chooses mode, density, text size and motion (spec 008) | Tenant membership |
| Designers, UX writers, researchers | Apply the guidelines and run design tests | Not a product role |
| Developers | Build with the components and pass the gates | Not a product role |

## 4. User scenarios

### User Story 1: Choose a design for the workspace (Priority: P1, R1)

A ministry's tenant administrator opens Administration, Brand, sees four design cards with live miniatures, chooses Atlas, checks the preview and contrast table, and saves. Every employee then sees the formal green design with top navigation, in Arabic and English, light and dark.

**Independent test:** set `design.preset` to each design on a test tenant through the brand API; the home and gallery show the design's attributes, fonts and accent, with no serious accessibility violation.

**Acceptance scenarios:**
1. **Given** the brand manager, **When** it opens, **Then** the four designs show with name, description, navigation style and a miniature drawn from the design's own resolved tokens, and the current design is marked. *(DLS-001)*
2. **Given** an administrator chooses a design, **Then** the editor replaces the token values changed so far with the design, keeps the brand name and images, reruns the checks and shows the preview; nothing reaches employees until saved. *(DLS-002)*
3. **Given** a saved design, **Then** pages render with that design's tokens and navigation style, and the brand version and audit record name the change. *(DLS-003)*
4. **Given** a tenant on Atlas sets its own accent color, **Then** the accent wins over the design and every other value stays Atlas. *(DLS-004)*
5. **Given** the tenant locked `design.preset`, **When** an organization chooses another design, **Then** the child choice is ignored and the impact view says so. *(DLS-005)*

### User Story 2: Build a screen with the system (Priority: P1, R1)

A developer builds a new page from a template and the shared components; the build fails when they use a raw colour, an inline SVG icon, an image without alternative text or a literal string.

**Acceptance scenarios:**
1. **Given** a component outside the system's rules, **When** `npm run verify` runs, **Then** it fails with the rule and the fix. *(DLS-010)*
2. **Given** the gallery, **Then** it shows every shared component, the icon set, the colour and type tokens and the template patterns in the tenant's active design. *(DLS-008)*

### User Story 3: Test the design (Priority: P1, R1)

**Acceptance scenarios:**
1. **Given** a pull request, **When** CI runs the design suite, **Then** each design in each language passes axe with no serious or critical violation, has no horizontal scrolling at 375, 768 and 1440 px, has no control under 24 by 24 px, and matches the reviewed gallery baselines. *(DLS-012 to DLS-015)*
2. **Given** a feature's first build, **Then** the designer and developer run the post-development review with generated screenshots and record the outcome on the pull request. *(DLS-017)*

### Edge cases and exception flows
- An older brand names a design that no longer exists: the default design applies and the token appears in the invalid token log (spec 033 fallback).
- A tenant changes an Atlas token so a pair fails contrast: the existing spec 033 blocking or warning rules apply.
- A font file fails to load: the fallback stack of the script renders.
- A design is chosen at organization scope without `experience.org_branding`: refused as any organization override is.

## 5. Functional requirements

- **DLS-001**: The brand manager MUST present the four designs with a live miniature, description and navigation style, and mark the current one.
- **DLS-002**: Choosing a design MUST be a token change (`design.preset`) validated, checked, versioned, audited and reversible like any brand change (spec 033 FR-012).
- **DLS-003**: The theme resolver MUST apply the design's values between the platform defaults and the tenant brand (spec 033 FR-030).
- **DLS-004**: Brand and organization values MUST win over the design's values.
- **DLS-005**: `design.preset` and `layout.navigation` MUST be lockable and inheritable like any token.
- **DLS-006**: Each design MUST define every colour in light and dark mode and pass every contrast and text size check of spec 033 FR-009 in strict mode.
- **DLS-007**: The four designs MUST differ in palette, typography, shape and elevation, and in the presentation variants of their descriptor (DLS-110), and MAY share a navigation style (Pulse and Studio both use the labelled sidebar, dark and light). They MUST NOT differ in behavior, content, permissions, available actions or information architecture.
- **DLS-008**: The web app MUST provide shared components for actions, text boxes, selections, cards, badges, avatars, alerts, images, tabs, icons and states, and a gallery showing them in the active design.
- **DLS-009**: Components MUST read only `--tb-*` tokens; per-design structural rules MUST live in one file.
- **DLS-010**: The build MUST fail on raw colours or sizes, literal font families or sizes, inline SVG outside the icon set, images without alternative text, literal user-facing strings and missing translations.
- **DLS-011**: Images MUST render with a fixed aspect ratio and lazy loading below the fold.
- **DLS-012**: CI MUST run axe on the home and gallery in every design and launch language, failing on serious or critical violations.
- **DLS-013**: CI MUST check for horizontal scrolling at phone, tablet and desktop widths in every design and direction.
- **DLS-014**: CI MUST check that interactive controls in the gallery are at least 24 by 24 CSS pixels.
- **DLS-015**: CI MUST compare gallery sections against reviewed visual baselines per design and direction.
- **DLS-016**: The design guidelines MUST cover typography, colour, icons, imagery, content, layout, actions and accessibility; the technical guidelines MUST cover frontend practice, security, performance and consistency.
- **DLS-017**: The testing strategy MUST define user-centric, accessibility, content, responsive, post-development and consistency tests with owners and gates.
- **DLS-018**: Every spec with a user interface MUST reference the design system in its UX section and list any new component or token it needs.
- **DLS-019**: New components, tokens or designs MUST update the guidelines, gallery and tests in the same change.
- **DLS-020**: Fonts MUST be self-hosted from the approved list and loaded per script on demand (ADR-0019, ADR-0021).
- **DLS-021**: All four designs MUST be available in every package.
- **DLS-022**: The design suite SHOULD write review screenshots on request for the post-development review.
- **DLS-025**: Every page MUST sit in the page frame: content up to 90rem wide, centred, with `space.lg` side padding (`space.md` on phones). Full-bleed sections paint to the edge but align their content to the frame.
- **DLS-026**: Module pages MUST be built from four page templates (List, Catalogue, Directory, Detail) and the shared page parts: page header (icon tile, h1, description, actions), section tabs, filter bar, data table, tile card, list rows, person card and split view (main column with a side column).
- **DLS-027**: Links MUST use `color.link` and carry no underline when their position says they are links (titles, tabs, navigation, cards); links inside running text keep an underline.
- **DLS-028**: The home MUST use the briefing hero (night surface), Your day tiles in the warm, cool and fresh tints, featured news and the campaign band, each from shared tokens only (`color.tint.*`, `color.surface.night`, `color.text.on_night`, `color.highlight.bright`, `color.surface.campaign`), with every pair checked for contrast in every design and mode.
- **DLS-029**: Names and other values that may be in another script MUST be isolated in sentences (`isolate()` in `lib/bidi.ts`, or `<bdi>` in markup) so an Arabic name does not reorder an English sentence and the other way round.
- **DLS-030**: Studio MUST be a design like the others: a token set chosen with `design.preset`, neutral surfaces, one blue accent, Inter with IBM Plex Sans Arabic, hairline borders and a light labelled sidebar. Its finish (a soft shade and a light top edge on filled buttons and the current sidebar page) MUST be drawn from its own tokens, so a tenant accent keeps the finish.
- **DLS-031**: Every component of the catalogue MUST be built once in `src/Web/components/ui` (parts used by one feature only in that feature's folder), read only `--tb-*` tokens, take all text from messages, and look right in every design, both directions and both modes. Where a component for the pattern exists it MUST be extended, not duplicated.
- **DLS-032**: Interactive behavior MUST use native elements first (`button`, `input`, `select`, `details`, `dialog`, the Popover API) and shared hooks for what the platform lacks (roving focus, type ahead, dismissal, focus return). The web app MUST NOT add a component library, a CSS framework or a behavior library for these components (constitution XXII).
- **DLS-033**: Actions: Button MUST offer the sizes medium (44 px), small (36 px) and compact (28 px, only inside toolbars, tables and dense panels), a leading or trailing icon, an icon-only form with a required accessible name, and a link form. The system MUST provide a button group, an icon button and a close button.
- **DLS-034**: Selection: checkbox (with indeterminate), radio group, switch, each also as a card with a description; segmented control; slider; chip (static, removable, selectable) and tag group; all operable by keyboard as their WAI-ARIA patterns describe.
- **DLS-035**: Text entry: text boxes with leading and trailing parts, search field with clear, number field with steppers, one-time code field with paste, time field, color field with presets, and file upload with drag and drop, validation messages and progress. Validation rules come from the API; the components only show them.
- **DLS-036**: Pickers and menus: menu (with groups, checked items and submenus), context menu, combobox with filtering, command palette opened from the shell search shortcut, and tree view. Date components (calendar, date field, date range field, slot picker) MUST format through `Intl` in the user's locale and the tenant's calendar, including the Hijri calendar, and MUST mirror in right to left.
- **DLS-037**: Overlays: dialog, drawer from any edge, popover, tooltip, announcement banner and the notification card form of messages. Overlays MUST trap and return focus, close on Escape, and never open over the element that has focus without moving focus into them.
- **DLS-038**: Structure and status: accordion, breadcrumb with collapsing levels, pagination, divider, carousel with snap and visible controls, tabs with a sliding indicator, icons and counts, sortable and selectable data table; avatar groups and presence, status dot, keyboard key, spinner, progress and meter.
- **DLS-039**: Data blocks: data table with toolbar, filters, column visibility and paging; data grid; stat cards with change against the previous period; month and week calendar; task list; notification panel; settings dialog; sign-in card. Assistant and agent parts: thinking indicator, composer with attachments, source list, usage limits, question steps, agent form and run progress. Blocks receive data and callbacks from their feature and hold no business rule.
- **DLS-040**: Charts MUST be TeamBeats SVG components inside a chart card (area, line, bar, bar list, combined, funnel, heat map, radar, radial, flow, scatter, rings, contributions, stage bars, steps), colored only from categorical chart tokens (`color.chart.1` to `color.chart.8`, `color.chart.track`) defined in every design for both modes, and MUST carry a text or table alternative. Color MUST NOT be the only way to tell series apart.
- **DLS-041**: Motion finish: selection indicators slide, filled buttons shade on hover, overlays fade and move a short distance, all with the motion tokens and only `transform` and `opacity`; everything stops when the user asked for reduced motion.
- **DLS-042**: Detail quality: every screen MUST pass the detail checklist in `docs/design-system/foundations/details.md` before it merges, and the design suite MUST cover the shell panels, list rows, forms and empty states it names.
- **DLS-043**: Values MUST be shown in people's words, never as machine values: languages through `Intl.DisplayNames`, dates and times through `Intl.DateTimeFormat` in the reader's locale (long style on profiles and articles, medium in lists), times within the last week as relative time with the full date on hover, time zones by city name and offset, and numbers through `Intl.NumberFormat`. Codes such as `en-US`, `2015-11-01` or `Africa/Cairo` MUST NOT reach the screen.
- **DLS-044**: Links placed as titles, rows, breadcrumbs, menus and chips MUST NOT be underlined (DLS-027); a link inside a sentence that starts an action (connect, edit, view) MUST be a button instead. Breadcrumbs MUST use muted text with chevron separators that mirror in right to left, and the current page in primary text.
- **DLS-045**: Overlays MUST follow one overlay model for the whole app: one shell bar panel open at a time (spec 008 FR-060); Escape closes the open overlay and returns focus to its trigger; an outside press closes a non-modal popover and its trigger toggles it; panels flip and shift to stay at least 8px inside the window; under 40rem wide a shell panel opens as a bottom sheet; every overlay uses the strong elevation (`shadow.md`), `radius.md` (12px), a 1px border and one stacking layer above the page; the assistant launcher hides while a shell panel is open. Panels share one surface: a header row with the title and at most one action that stays fixed, a body that alone scrolls with a thin scrollbar, and an optional footer bar with a divider.
- **DLS-046**: Notifications MUST open as an inbox popover anchored to the bell, 26rem wide (400 to 440px) and at most the lesser of 40rem or 75% of the window tall, with tabs All, Unread and Action needed, and groups Needs your action, Today and Earlier. A row (76 to 104px) shows a 34px category icon tile, the title clamped to two lines, one muted meta line (reference, a middle dot, the step or category) and a relative time at the end; unread is a 6px accent dot plus a semibold title, read rows are regular weight, never a tinted box or a thick border; overdue and due items carry a small status badge. Hovering or focusing a row reveals its actions (Review, Mark as read) without moving the text. Opening a row goes straight to its request, policy or task.
- **DLS-047**: The settings button MUST open Quick preferences, a compact popover (about 21rem) with only appearance and density as segmented controls, language and text size as compact setting rows (label at the start, the value as a small select at the end), reduce motion as a switch, and an "All preferences" footer link to the personal settings page. Integrations such as Outlook belong in the Connected apps section of the personal Preferences page (`/settings`), and resetting personal pages belongs on the same page with a confirmation; neither appears in Quick preferences. Language is chosen in one place. The account menu MUST be a compact menu (about 17.5rem) with a profile header (avatar, name, job title, email), menu rows for My profile, Preferences and, for people with an admin section, Administration (spec 008 FR-062), and Sign out as a plain row after a divider; an organization switcher appears only for people with more than one organization.
- **DLS-048**: Status MUST be a badge with a tone that follows the state (success for approved and completed, warning for returned and overdue, danger for rejected, info for in progress, neutral for drafts and cancelled), never coloured text alone and never an outlined box.
- **DLS-049**: Rows in a list MUST use the list rows part: one title link without underline, a status badge, one muted meta line whose facts are separated by a middle dot, and a trailing chevron when the row opens a page. Separate facts MUST NOT run together in one string.
- **DLS-050**: Floating actions such as Ask TeamBeats MUST NOT cover content at the end of a page: the page frame keeps space for them at its end, and on phones they shrink to an icon button with a visible tooltip and the same accessible name.
- **DLS-051**: Form controls: hints MUST sit under their control so a row of controls lines up; inside a filter bar a hint becomes the placeholder. Fields in a row lose their bottom margin so buttons line up with controls. Native radios and checkboxes MUST get the system look (size, border, accent fill, focus ring); a yes or no answer such as "Was this helpful?" MUST be two toggle buttons; a sort direction MUST be an icon button with `aria-pressed`, not a checkbox. Required fields carry a small "Required" tag.
- **DLS-052**: Buttons MUST keep their natural width; one primary action per area, start aligned with the secondary actions beside it at the same height. Full-width buttons are only for phones and sign-in cards.
- **DLS-053**: Empty, error and denied states MUST show an icon tile, a title and one line of help, without a dashed border, and an action when there is one. A card that would otherwise end half empty MUST fill its space with its empty state.
- **DLS-054**: Forms and reading pages MUST sit in a readable column (forms at most 44rem, article text at most 46rem) inside the page frame; detail pages use the page header with the record's icon and breadcrumbs, not the section tabs of the area.
- **DLS-055**: Person cards and other cards with an avatar MUST align the avatar to the top of the text, so names line up whether a card has one line or three.
- **DLS-056**: The shell bar and the navigation rail MUST read as one frame, with no lines between them, and the page MUST sit inside that frame with a rounded start corner (`radius.lg`) so the join matches the rounded cards. The current rail item is an inset pill with space on every side. Page actions such as "Arrange this page" are icon buttons in the bar next to settings, never a row of their own.
- **DLS-057**: Editors that move items (personalization mode, the page builder) MUST give each movable item a drag handle (the menu icon), fade the item while it moves and draw an accent bar where it will land, and MUST keep the same moves as buttons for the keyboard.
- **DLS-058**: Geometry and spacing: page cards use `radius.lg` (16px), popovers, sheets, tiles and inner cards `radius.md` (12px), inputs and buttons `radius.sm` (8px), badges 6px; fully rounded shapes are only for the avatar, the count bubble and the assistant launcher. Spacing uses the 4px scale (4, 8, 12, 16, 24, 32, 48); card padding is 16 to 24px, page gutters 24 to 32px, inputs and selects 40px high (36px compact); buttons keep the DLS-033 sizes (medium 44px, small 36px, compact 28px).
- **DLS-059**: Type scale: page title 28 to 32px semibold, section heading 18 to 20px semibold, card and row title 14 to 16px semibold, app body 14 to 16px by density, reading text 16px, meta 12 to 13px in the secondary text colour. Bold (700) is for numbers in stat tiles only.
- **DLS-060**: Colour roles: the accent marks selection, focus and the one main action of an area; structure (borders, dividers, surfaces) is neutral; semantic colours carry meaning only. Icons sit in a tinted tile only where the tile identifies a kind of thing (service category, notification category, file type); navigation, menus and toolbars use bare icons (16px in meta, 18 to 20px in actions, 20 to 24px in navigation).
- **DLS-061**: States: hover on a card or row changes its border or surface, never its size or position; a selected navigation item uses the soft accent surface, a semibold label and the accent icon, not a large solid fill; every component defines hover, focus, disabled, loading (a skeleton in the content's shape), empty and error states; motion for hover, menus and overlays lasts 120 to 200ms and stops under reduced motion.
- **DLS-062**: Work items: tasks, approvals and requests MUST use one shared work item part with a card form (up to six items, with type icon, title, reference, status badge, the process steps as a segmented progress line when the API returns them, the important date and the next action) and a row form for longer lists (aligned columns: item, status, current step, due, action). Progress comes from the process definition the API returns, never from the status. Request lists filter with a segmented Active, Completed, All control plus a status filter control, a search box and a sort control, not one chip per status.
- **DLS-063**: Catalogues: the services catalogue MUST show favourites and recent services as one compact strip, categories as tabs with counts, and a grid or list view switch; a service card puts the name first, the description in at most two lines, the favourite star at the top end, and the next step (approval, time to complete, or "opens another system") in its footer, with the primary action revealed on hover or focus.
- **DLS-064**: Records: a person's profile MUST open with an identity header (photo or initials, name, title, department, office, manager and contact actions) and group fields into Work information, Contact details and Personal preferences; a field's source is said once per group ("Managed by the directory"), and a field's visibility appears as a small icon label only where it is narrower than everyone. Read-only fields read as information, not as disabled inputs; editable fields are grouped with one Save.
- **DLS-065**: Reading and files: an article MUST put its text in a reading column with its meta line and an Edit action in the header, an "On this page" list and related items in a side column on wide screens, and the helpfulness question at the end of the text. A document library MUST read as a file browser: breadcrumbs to the folder, compact filter controls, sort with a direction button, rows with a file or folder icon, name, type, owner and change date, and an empty state that names the filter and offers Clear filters.
- **DLS-066**: The assistant launcher MUST be compact (40px high, "Ask" with the AI mark), MUST NOT cover content, the footer or an open overlay (it sits in the shell bar, DLS-078), and SHOULD offer help that fits the page it is on (completing a service, explaining a policy, the next step of a request).
- **DLS-067**: UX quality gate: a screen merges only when no floating panel overlaps another, nothing is clipped at phone, tablet and desktop widths, shared parts use tokens, every component has its states, compact and comfortable densities size components consistently, Arabic right to left, light and dark modes and text scaling work, the assistant launcher covers nothing, existing workflows and permissions are unchanged, and the key journeys pass the visual and keyboard tests of the design suite.
- **DLS-068**: Catalogue screens (the Plan page, permission lists, any list of system capabilities) MUST show each item by its localized name, never its technical key, and every catalogue item MUST have a name in each launch language (checked by `npm run check:messages`). A list longer than about twenty items MUST offer a search by name and filters with counts, group items by area with an "x of y" count per group, sort groups and items by their localized names, flow the groups in two columns on wide screens, and show an empty state with a way back when nothing matches. A summary row keeps to the stats that fit one row at the content width (at most three on an admin page); secondary facts such as a version go in the meta line.
- **DLS-069**: Calendar header: a calendar screen or card MUST put the title and the shown period (month and year) at the start, and previous, Today and next at the end, with a date picker on the period; the view switch (Agenda, Week, Month, and Team when the API offers it) is a segmented control under the header. Previous and next mirror in right to left.
- **DLS-070**: Calendar layers: each layer (meetings, company, department, important dates, holidays, my leave, team leave) MUST have its own chart token colour, its own icon and a text label; layer chips toggle with a pressed state and are the legend. Pending items use a dashed outline with a diagonal pattern; cancelled items use a strikethrough and the word "Cancelled". Meaning never depends on colour alone.
- **DLS-071**: Week strip and agenda rows: the week strip shows seven days with weekday initial and day number, the selected day on the soft accent surface, today marked by weight and `aria-current`, and up to four layer markers under each day with a hidden text count. Agenda rows are compact: a 3px layer bar at the start, the time or "All day" on the first line, the title, then the place or source; a row expands in place to its details and actions; at most one primary action (Join while a meeting is live).
- **DLS-072**: Month with ranges: multi-day leave and holidays MUST draw as one continuous bar across the days of each week row (rounded at the range start and end only), holidays get their own bar style apart from leave, single-day items show as markers with a "+N" count, and selecting a day opens the day panel. The month is a table with weekday column headers; each day cell has a full date label.
- **DLS-073**: Day panel and bottom sheet: selecting a date opens a side panel beside the calendar at widths of 900px and more, and a bottom sheet (the Drawer from the bottom edge, with a grab handle, focus trapped and Escape to close) on smaller widths. The panel lists the day's items as agenda rows.
- **DLS-074**: Team availability: managers see up to three stat cards (available today as x of y, on leave today, starting soon), a heatmap with one cell per day showing the available share as text and as a sequential chart token step, a warning icon and label on days under the staffing threshold, and an upcoming leave list (avatar, name, dates, status badge). Non-working days are shown as empty cells, not as 0%.
- **DLS-075**: A design MUST show on the pages people use, not only in the gallery. Home widgets and page parts MUST be built on the catalogue blocks where one exists (headline counts on `StatCards`, view switches inside a card on `SegmentedControl`, labels and counts on `Badge`), and each design's structural finish MUST reach the shared page surfaces. Studio's finish: every page card, tile, stat card, filter bar and row list is a white surface with a hairline and the soft shadow; section tabs are a segmented track with a raised white current page; icon boxes are white with a hairline and keep the tone in the glyph; stat cards stay white and carry the tone in their icon box; the briefing is a light card with bordered rows and Studio buttons instead of the night surface; the lead story is one white card. The rules live in `components/ui/designs.css` and read only tokens.
- **DLS-076**: Product marks: where a screen names an external product TeamBeats connects to (the Connections area, its wizard), it MAY show that product's published mark beside the name, unaltered (no recolouring, stretching or effects), at icon size on a plain plate with a thin border, stored locally under `public/connectors` with its source recorded in `docs/design-system/foundations/imagery.md`. The mark is decorative (empty `alt`) because the name is always written next to it. Types with no mark that can be reproduced faithfully (custom REST, webhooks, SFTP and file imports, generic HR and finance systems, and products whose owners do not publish a mark for this use) use an icon from the icon set on the same plate. Marks never stand in for TeamBeats or tenant branding.
- **DLS-077**: Wizards: a task that creates something in several dependent steps MUST show the steps as a numbered ordered list above the content (number in a circle, a check for done steps, the current one filled with the accent and bold, `aria-current="step"`, done and current also said in hidden text), one step per page address, a header that recalls what is being set up once it is saved, and a footer with the main action at the end side and quiet secondary actions before it. A choice of types is a grid of tile cards grouped under headings with a search; unavailable choices are listed apart with the reason, never as disabled links.
- **DLS-023**: R2: theme drafts (spec 033 US2) SHOULD show the design review checklist before approval.
- **DLS-024**: R2: cross-browser runs (Firefox, WebKit) SHOULD join the design suite once the browser matrix decision in `docs/testing/e2e-plan.md` is made.
- **DLS-078**: Floating layers: a floating element (the update notice, the push offer, toasts, the assistant launcher, cookie or consent notices) MUST NOT sit over page content, form controls or the footer. The assistant launcher lives in the shell bar, and notices that need the person's attention dock in a strip in the page flow under the shell bar, pushing content down instead of covering it. At most one notice shows at a time. Acceptance: at 390, 768 and 1280px no focusable element of the page, no card title and no footer text lies under a floating element; the design suite checks this on Home, a service form and the policy register.
- **DLS-079**: Responsive tables: every table MUST use the shared `DataTable`, which gives each column a priority. Below 640px the table renders each row as a stacked card (the first column as the card title, then the high priority columns as label and value pairs, then the row actions); between 640 and 1024px low priority columns are hidden and the table scrolls inside its own container, never the page. Header cells stick while the table scrolls. Text never breaks inside a word (`overflow-wrap: anywhere` and `word-break: break-all` are not used on table cells); identifiers such as email addresses are shown in full or wrap at their punctuation and are never clipped. Acceptance: at 390px the policy register and the admin People table show every key field with no word split mid word and no horizontal page scroll; at 900px no email address is clipped.
- **DLS-080**: Tab strips: section tabs (`SectionNav`) MUST keep every tab reachable at every width. When the tabs do not fit, the strip scrolls sideways inside itself with a fade at the edge that has more tabs, the current tab is scrolled into view on load, and the strip mirrors in right to left. Acceptance: at 390px every tab of Services, Tasks, Documents and People can be reached by touch, by the keyboard and by a screen reader, and a fade shows while tabs are hidden.
- **DLS-081**: Icons carry meaning: one icon per concept across the product, one stroke weight and the icon size scale. A list of different things of the same kind (services, libraries, admin sections) MUST NOT repeat an icon for two different items when the icon set has a better match, and a detail page header shows the same icon as its card. Acceptance: on the staging catalogue no two services share an icon, and each service page header shows its card's icon.
- **DLS-082**: Dates: every date MUST be written by the shared formatter (`lib/format.ts`) in the viewer's locale with the month as a word, never as all digits (13 Nov 2026 in dense tables, 13 November 2026 in text, with the weekday where the day matters). A date field also writes the chosen date under the control in this form, because the browser's own date control follows the browser's language, not the person's. Acceptance: no screen shows a date such as 11/13/26 or 13/11/2026; a search of the web app finds no `toLocaleDateString` outside the formatter.
- **DLS-083**: Validation messages: a field error MUST name the field and say what to enter ("Choose a leave type", "Enter the end date"), never only "This field is required". On a failed submit, focus moves to the first field in error and an error summary at the top of the form lists every error as a link to its field. Acceptance: the leave request form submitted empty names each missing field and focuses the first one.
- **DLS-084**: Destructive actions: an action that deletes or discards data uses the danger tone in outline or quiet form; a solid danger button appears only inside the confirmation dialog. Bulk deletes (delete all, clear history) live in a menu or a settings area, never beside the primary action, and their confirmation states what will be removed and how many items ("Delete 12 conversations?"). Acceptance: the assistant page shows no solid danger button until the confirmation dialog is open.
- **DLS-085**: Touch targets: on a coarse pointer or below 640px every interactive control MUST have a hit area of at least 44 by 44px (the visible control may be smaller; the hit area grows with padding or a pseudo element), and controls in a row keep at least 8px between hit areas. Acceptance: the design suite's target size check at 390px reports no control under 44px on Home, Services, Tasks and People.
- **DLS-086**: Stat grids: a row of stat cards or KPI tiles MUST use an auto fit grid with a 140px minimum card width, so a card moves whole to the next row instead of squeezing, and a label wraps only between words. Acceptance: at comfortable density on Home every Your day tile keeps its label whole at 390, 768 and 1280px.
- **DLS-087**: Empty states: an empty list or a search with no results MUST say why it is empty and offer one next step (Clear search, Clear filters, Browse all services), as in DLS-065. Acceptance: a people or services search with no match shows the reason and a Clear search action.
- **DLS-088**: Decoration: the AI mark (the four point spark) appears only on actions and content produced by AI (Ask, AI answers, AI drafts), never as a background watermark or ornament. Content cards with no picture of their own use a typographic card (title, category tone, date) instead of a generic illustration; the tenant's own photos and the item's own picture are always preferred. Acceptance: the home briefing has no watermark, and no news or campaign card on staging shows a stock illustration.
- **DLS-089**: One widget frame: every home widget (every spec 032 placement) and every card-like section of an inner page that lists records MUST be built on the shared `Widget` frame in `components/ui` (a section named by its heading, an optional count `Badge`, at most one header action, the body, and an optional footer link that opens the full page). A placement or feature MUST NOT define its own card surface (background, padding, radius, shadow) or header layout; each design's finish targets the frame (`.ui-widget`), not a list of feature classes. Banners and content blocks (call to action, announcement, briefing, the featured news layout, rich text) are the only exception and use their own catalogue block. Acceptance: `npm run check:design` fails when a placement renders a `section` or `article` outside the frame, and Home in the four designs shows every widget with the same surface, header and footer link.
- **DLS-090**: One row per kind of record: a kind of record (calendar item, mail message, task, person, document, service) MUST have one row part in `components/ui` or its feature's `shared` file, and every surface that lists that kind (home widgets, Your day, inner pages, spaces, the workspace) MUST use it, passing only data and labels. Calendar items of any source use `AgendaRow` (DLS-071); a second month or agenda drawing is not allowed (spaces use `RangeMonth` like the calendar workspace). A widget list is capped (calendar items 5, mail 10, other lists 5 by default) and ends in a "See N more" or "Open" footer link instead of growing; a widget never lists more than one day of a calendar. Acceptance: My calendar, the calendar card, Your day and the space calendar draw calendar items with the same row, and no home widget is taller than its list cap.
- **DLS-091**: Mixed-direction rows: a name, subject or title in a row MUST be isolated (`bdi`, direction from its own text) and MUST align to the start of the row in the page's direction (the row places the isolated box at its start; the text's own alignment would follow the text's direction), so an Arabic subject in an English row and an English subject in an Arabic row start at the same edge as their neighbours, with dates and times at the end. Acceptance: My mail with Arabic and English subjects aligns every sender and subject to the start in both languages.
- **DLS-100**: Page hierarchy. Every page MUST be composed in three levels and show them in this order of visual weight: the primary action or decision (what the person must do or the answer they came for), the supporting context (what helps them do it), and optional discovery (what they may also want). The primary level sits in the first viewport at 1440 by 900 and at 390 by 844 px, takes the widest region, and holds the page's one primary button. Equal white cards for every data set are not a composition. Each spec with a user interface states the three levels of each screen, and the design review checks them. Acceptance: on Home, Tasks, Services, Calendar, People, Policies, Documents, Knowledge and the Assistant, the first viewport shows the primary level and at least one supporting item without scrolling.
- **DLS-101**: Content budgets. A summary component (any placement on a home, dashboard or overview page, and any side panel list) MUST show at most its budget of items and then a path to the full view ("View all" with the total count). The budgets are: 3 items in a quarter width region, 5 in a half width region, 8 in a full width region; a strip of tiles shows one row (4 to 6 tiles); calendar and mail summaries show at most 5 and count as lists. A component manifest MAY lower its budget and MUST NOT raise it (spec 032 FR-071). The shared `Widget` frame enforces the budget, so a feature cannot exceed it by passing more rows. A summary never scrolls inside itself and never grows the page without limit; an empty summary collapses to its empty state at its natural height and MUST NOT hold a blank area taller than 96 px. Acceptance: with 30 tasks and 20 meetings the home is at most 2.5 viewports tall at 1440 px and at most 6 at 390 px, and every list ends in a View all link with the count.
- **DLS-102**: One instance per data source. A page MUST NOT show the same data source twice (two mail lists, two calendars, the same count as a stat tile and again as a sentence) unless the placements are declared as different views of it (for example the month grid and the day agenda of one calendar). The renderer drops the later duplicate and records it, the page builder warns before saving (spec 032 FR-072), and home suggestions skip sources a view already shows (spec 032 FR-070). A headline number appears once: where the briefing says how many items wait, the side panel shows what is next instead of the same counts. Acceptance: no reference home view shows a source twice; adding a second mail component to a view shows the warning.
- **DLS-103**: State completeness. Every shared component and every placement MUST define and build these states: first load (a skeleton in the shape of the content, reserving its space), empty (why, and one next step), partial data (what is missing, the rest usable), stale (when it was last updated, with a refresh), error (what failed, with Retry, contained in the component so the page and its neighbours keep working), denied (no names or counts leaked), success (a positive confirmation, not a blank: "You are up to date"), disabled, pending during an action, long text and long names in Arabic and English, a narrow container, keyboard focus, dark mode and right to left. Placement states use `StateView` inside the `Widget` frame at the frame's normal size. A missing state blocks the merge like a failing test.
- **DLS-104**: Type roles and the size floor. Text uses named roles mapped to the type tokens, and nothing else: page title (`font.size.xxl`, semibold), section title (`font.size.xl`), card and widget title (`font.size.lg` or `md`, semibold), row title (`font.size.md` or `sm`, semibold), body (`font.size.md`), secondary line and table cell (`font.size.sm`), meta and labels (`font.size.xs`), and the data number of a stat (`font.size.xl`, bold). A page uses one page title size; at most five sizes appear on one screen. `font.size.xs` MUST be at least 12 px and `font.size.md` at least 14 px in every design, mode and density, checked by the theme engine. Buttons, selects, text boxes, date controls and every other native control MUST inherit the design's font family and take their size from a token, so no browser default font or size reaches the screen. Acceptance: on every page of the design suite no text is under 12 px and the only font families are the design's own.
- **DLS-105**: Page frame. Every page, for employees and administrators, MUST use one frame: the content inset of DLS-025, a footer that sits at the end of the window on short pages and after the content on long ones, and the page header of DLS-026 with the same structure everywhere (icon tile, title, optional one line description, actions at the end, then section tabs, then one divider). Breadcrumbs appear only on pages deeper than one level; a top-level page MUST NOT show a one-item breadcrumb that repeats its title. The current navigation item uses the soft accent surface of DLS-061 in every design, including each design's own finish. A page MUST NOT set its own inset, title size or header layout. Acceptance: on a page with little content the footer touches the end of the window; Assistant and Notifications have the same header and inset as People.
- **DLS-106**: Toolbar-first filters. Searching and filtering a list MUST use the shared filter toolbar: one row with the search box first (the label is hidden and the hint is the placeholder), then at most three filters as compact selects or segmented controls at the height of the search box, then view and sort controls at the end. Further filters open from a "Filters" button with a count. Applied filters show as removable chips under the row with "Clear all". Filters apply as they change; a list that needs a submit shows one compact Search button in the row. The toolbar is not a card and is at most 56 px tall on desktop; on phones the search box stays and the filters move behind the Filters button. Acceptance: People, Policies, Documents, Requests, Services and the admin lists use the toolbar; the list starts within 220 px of the top of the content area at 1440 px.
- **DLS-107**: Pattern choice. The pattern for a kind of information MUST come from the table in `docs/design-system/foundations/composition.md`: one count with a next action is a labelled number with its action; a trend is a number with a sparkline and a comparison; a status across stages is a progress line with owner, age and next step; comparable categories are a ranked bar list; today's appointments are a short time-ordered agenda; availability across days is a week or month view; two to six frequent destinations are icon and title shortcuts; long searchable records are a dense table or list with the toolbar; a story or spotlight is an image-led editorial unit; a task needing explanation is a guided form. Cards are for discrete things a person browses and picks (services, people, spaces, libraries), never for records, settings or text. A grid of cards that all share one icon and one line of meta MUST be a list.
- **DLS-108**: Work rows act. Every row that represents work waiting for the person (an approval, a task, an attestation, a request returned to them) MUST show its next allowed action as a button in the row: Review for anything that needs reading before a decision, Open for a task, Acknowledge only where the content is on screen. Review and Approve are different actions: Approve and Reject appear only where the request's details are visible. Review opens the item in a side panel (a `Drawer` from the end edge; a full page on phones) so the queue keeps its place, and after a decision the panel closes, the row leaves with a message that offers Undo where the workflow allows it, and focus moves to the next row. A row shows the type icon of its request type, the title, the requester, the step, and the due date with its age ("Due 4 Nov, 10 days late"); overdue rows come first. Bulk "All tasks" style buttons MUST NOT repeat on each row.
- **DLS-109**: Uniform values step back. Where every row of a table or list has the same value in a column (all "Published", all the same owner), the column is hidden and the value is said once above the table, or shown in a muted form; the filter for it stays available. A register or list page opens with what needs attention (overdue reviews, items waiting for the reader) before the full list.
- **DLS-110**: Design descriptor. Each design MUST declare, beside its tokens and navigation style, a descriptor of typed values: its default density, its imagery approach (image led, balanced, or typographic), and the presentation variant it uses for each part in a fixed list: news lead (`editorial` with a large picture, `compact` with a thumbnail, `typographic` with no picture), stat tiles (`tinted`, `outlined`, `plain`), work rows (`comfortable`, `dense`), section tabs (`underline`, `segmented`), page cards (`raised`, `outlined`, `flat`) and the briefing (`night`, `light`). The descriptor is stored as choice tokens (`variant.*`, `density.default`, `imagery.style`), resolved, locked and inherited like any token (spec 033 FR-032). A variant changes presentation only: every variant of a part receives the same data, offers the same actions in the same order and has the same accessible names. Tenants MAY override a variant with another value from the list. The four descriptors: Beats balanced and comfortable (editorial, tinted, comfortable, underline, raised, night); Atlas formal and structured (compact, outlined, comfortable, underline, outlined, light); Pulse editorial and image led (editorial, tinted, comfortable, segmented, raised, night); Studio operational and dense (compact, plain, dense, segmented, outlined, light). Acceptance: switching design changes the composition of the home's news lead, stat tiles and work rows, and the same tasks, counts and actions are present in all four.
- **DLS-111**: Visualization. Numbers that compare or change MUST be drawn with the chart parts of DLS-040 chosen by the DLS-107 table, each with a text equivalent, a unit and a comparison or denominator ("3 of 12", "up 4 from last week"). Charts MUST NOT be decoration: no ring or gauge for a single count, no chart without a decision it helps, whole number ticks for counts, and a single data point is shown as a number, not a chart.
- **DLS-112**: Editorial. A story page MUST lead with its content: kind label (feature, announcement, update, event, urgent notice), title, a byline with author, date and reading time, an optional hero picture at 16:9 with alternative text (when there is none the title simply follows the header, never a coloured placeholder), then the text in the reading column. Reactions are one compact row of buttons with counts under the text. Comments use one composer with mentions typed inline with `@` and a suggestion list, never a separate mention field; the composer starts at one line and grows. AI help (summarize, translate, ask) is a quiet row of buttons with the AI mark in the header area, not a card. By default the article text takes more of the first viewport than the social parts.
- **DLS-113**: Identity. A person appears as one of three forms of the person part: chip (avatar and name), row (avatar, name, title, unit) and card (adds office and up to two quick actions among email, chat and call, shown only for channels the person has and the viewer may use). Presence and location show only where the directory allows. Directory results offer list and grid; a search shows results first and discovery content (new joiners) after them.
- **DLS-114**: Assistant. The assistant page MUST be one conversation workspace built on the assistant parts of DLS-039: the transcript, then one composer with Send, starter suggestions when the conversation is empty, and text tools (rewrite, translate, summarize, explain, draft) as modes of the same composer, never a second form. An answer shows its sources as titled links with their kind and date; when the sources do not support an answer the assistant says it cannot verify it and offers the nearest sources, and that state has its own look. An action by the assistant shows plan, steps, the approval it needs and the result, and nothing irreversible runs without the person's confirmation. Generated text is labelled as generated wherever it sits beside official records.
- **DLS-115**: Form levels. A form uses one of three levels: inline (one or two fields changed in place, saved on blur or with a small Save), standard (grouped fields in the readable column with one primary action), or guided (several dependent steps in a dialog or wizard, DLS-077, ending in a summary before the commit and a receipt after it). Rare, consequential tasks set beside a list (delegation, bulk changes) MUST be a compact summary with one button that opens a guided dialog, not a permanent form beside the list.
- **DLS-116**: One system for administration and employee screens. Administration pages MUST use the same frame, page header, tabs, toolbar, tables, tags, forms, empty states and type roles as employee pages; the gates and the design suite cover both. Differences are limited to the administration navigation and a higher default density of tables.
- **DLS-117**: State coverage in the gallery. The gallery MUST show each shared component in each state of DLS-103 that applies to it, and a component's entry in `docs/design-system/components.md` lists its states. The design gate fails when a component file in `components/ui` has no gallery entry.
- **DLS-118**: Gates on real pages. The design gate (`npm run check:design`) MUST also fail on: a page under `app/` that renders no shared page header; a feature style sheet that declares its own card surface, tab strip, tag or filter bar instead of the shared part; a literal font size or a size outside the type roles. The design suite MUST run axe, the reflow check, the target size check, the text size floor and the font family check on the main pages (Home, Tasks, Services, Requests, Calendar, Assistant, People, Policies, Documents, Knowledge, Notifications, Preferences, and the Administration overview, Users and Plan pages) in each design, in Arabic and English, at comfortable and compact density, at 390, 768 and 1440 px, with visual baselines for the first viewport of each page in the default design. A high-volume scenario (30 tasks, 20 meetings, 40 notifications) checks the budgets of DLS-101.
- **DLS-119**: Calendar views. Beyond DLS-069 to DLS-074: an item that spans several days appears once in the agenda under its first shown day with its date range, not once per day; recurring identical items within the shown period collapse to one row with their count where the view is a summary; overlapping items in the week view sit side by side at equal widths with at least the title readable, and beyond three share a "+N" block that opens the day panel; a month cell shows at most three items and then "+N more". A calendar page shows one agenda for the selected range, never a second list under the grid. A title in another script starts at the same edge as the other titles (DLS-029). The home shows the summary variant only: today and the next item, at most five rows.

## 6. Business and validation rules
- `design.preset` takes `beats`, `atlas`, `pulse` or `studio`; `layout.navigation` takes `rail`, `top` or `sidebar`. Other values are refused with `validation.theme.choice_invalid`.
- The descriptor tokens of DLS-110 take only the listed values and are refused otherwise with the same code. `font.size.xs` under 12 px or `font.size.md` under 14 px in any density is refused with `validation.theme.text_too_small`.
- Content budgets are platform limits: a manifest or a placement can lower them, never raise them.
- A new tenant, and any brand that sets no design, uses Beats.
- Choosing a design in the editor replaces the brand's token values; brand name, assets and contrast policy stay.

## 7. Tenant and organization scope
- The design is a token of the tenant brand profile and of organization overrides; it follows spec 033 section 7 for isolation, locks and inheritance.
- Cross-tenant denial: the same cases as spec 033 (theme CSS and assets of another tenant are not found).

## 8. Data, ownership and classification
No new data. The design is stored as a token in the brand version (spec 033 section 8).

## 9. Package entitlements
All four designs are in every package (smallest safe default: the design is part of tenant branding, which spec 033 puts in every package). Organization-level design choice needs `experience.org_branding`.

## 10. UX, localization and accessibility
- The guidelines in `docs/design-system` are the UX rules for every screen.
- Design names, descriptions and picker text are localized in Arabic and English.
- All four designs meet WCAG 2.2 AA in both directions and modes.

## 11. AI behavior and data policy
Not applicable. The AI mark (four point star) is reserved for AI features in every design.

## 12. Integrations and events
Design changes publish through `ThemePublished` like any brand change.

## 13. Audit, telemetry and analytics
`theme.published` audit records include the new brand version; the design is visible in the version's tokens. Invalid design values increment `theme.invalid_token`.

## 14. Security and abuse cases
- A design is a fixed, reviewed token set: it cannot add CSS, scripts or remote resources.
- Per-design CSS reads only tokens; fonts come only from the app's own origin under the CSP.

## 15. Non-functional requirements
- Theme CSS stays under 30 KB compressed per brand and mode with the new tokens.
- Fonts of designs a tenant does not use are not downloaded.
- Switching design causes no layout shift on load (theme in the head before paint).

## 16. Success criteria
- 100 percent of shared components appear in the gallery and pass the design suite in four designs and two languages.
- The main pages of DLS-118 pass the design suite in four designs, two languages and two densities.
- No reference home view shows a data source twice, and with 30 tasks and 20 meetings the home stays inside the DLS-101 budget.
- Release gates measured in moderated tests with employees (owner: product): at least 90 percent first attempt success on the priority journeys, and at least 85 percent of first-time users find a core service, a pending approval and a company policy unaided.
- Zero serious or critical axe violations on the home and gallery in every design.
- A tenant administrator can switch design in under one minute without help.

## 17. Open questions
- Should Firefox and WebKit join the design suite in R1 or R2? Default: R2 with the browser matrix decision.
- Should tenants be able to submit their own design? Default: no; they adjust one of the four through tokens; revisit with R3 token extensions.
- Is Studio the final name of the fourth design? Default: Studio, so no other company's brand name appears in the product.
