# Row-level security exceptions

Every table with a `tenant_id` column has RLS enabled and forced (`platform.enable_tenant_rls`). The tables below are the only exceptions. `tests/Security/DatabaseIsolationTests.cs` fails if any other table lacks forced RLS, and also fails if a table listed here gains RLS without being removed from the list.

| Table | Why it is not under RLS | Compensating control |
|---|---|---|
| `messaging.outbox` | The dispatcher reads pending messages for all tenants in one pass (ADR-0006). | Rows are written only inside the producing transaction, which already runs under the producer's tenant context. The `tenant_id` column travels as a message header and consumers re-establish context from it. `tb_app` cannot read payloads through any API. |
| `messaging.inbox` | Platform messages (for example `PackagePublished`) have no tenant, so inbox rows can carry a null `tenant_id`, which a tenant policy cannot express. | Holds only consumer name, message ID and tenant ID, no business data. |
| `messaging.dead_letter` | Written when tenant context is missing or invalid, which is exactly when RLS context cannot be set. | Operator-only diagnostics; no tenant API reads it. |
| `identity.verified_domain` | One tenant per verified email domain per installation (spec 003 section 6) must be enforced across tenants. | `tb_app` has SELECT only; writes are platform operations. Holds only the domain and the owning tenant ID. |
| `tenancy.domain_route` | A request on a custom domain (spec 033 FR-010) must find its tenant before any tenant context exists, and one host may belong to one tenant only. | `tb_app` has SELECT only. Rows change only through the security definer function `tenancy.sync_domain_route`, which reads the tenant's own `tenancy.tenant_domain` row under the caller's tenant context, so a tenant can route or unroute only a host it verified. Holds only the host, the tenant ID and the domain ID. |
| `integrations.teams_route` | A message to the TeamBeats bot in Teams (spec 014 US8) names only the person's Microsoft 365 directory, so the bot finds the tenants that reach Teams through it before any tenant context exists. | `tb_app` has SELECT only. Rows change only through the security definer trigger function `integrations.sync_teams_route`, which reads the writer's own connections under its tenant context. Holds only the directory ID and the tenant ID; the person is then found inside each tenant under RLS. |
| `analytics.benchmark_contribution` | Benchmarks across tenants (spec 021 R3) combine one figure per tenant that opted in, so the quartiles must read every such tenant's row. | `tb_app` has no privilege at all. Rows change only through the security definer functions `analytics.contribute_benchmark` and `analytics.withdraw_benchmarks`, which act on the caller's own tenant and only while its policy takes part; `analytics.benchmark_figures` returns only a count and, from five tenants, quartiles, to a tenant that takes part. Holds a tenant ID, a metric, a week and a whole tenant figure, never a person. |

Platform tables without a `tenant_id` column (`tenancy.tenant`, `entitlements.package*`, `ai.model_catalogue`, `ai.platform_route`, `audit.platform_audit_event`, `identity.platform_*`, `publicapi.verified_mcp_client`, `publicapi.platform_block`) are platform data by design and are changed only through platform-host endpoints guarded by `RequirePlatformOperator`. Tenant requests may read the catalogue tables (`ai.model_catalogue`, `ai.platform_route`, `publicapi.verified_mcp_client`, `publicapi.platform_block`), which hold no tenant data.
